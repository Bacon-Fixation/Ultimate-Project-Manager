SAFE DEFAULT

Back Up Before Write-Oriented Tools

Restore, recovery, dependency updates, PM2 controls, and Text Sanitizer are easier to use confidently when a recent verified backup already exists.

UPM skips unchanged backups, so creating a baseline before a risky operation does not require constantly duplicating identical archives.

STATUS TIP

Process Health Is Not Service Health

A PM2 process can be online while Redis, MariaDB, PostgreSQL, Docker, or an HTTP dependency is unavailable. Enable project Service Health when those dependencies matter to the application.

Getting Started & Dashboard TourRecommended first-run order and where information lives.
  1. Configure UPM itself. Use Settings for listener, storage roots, remote access, authentication, encryption, accessibility, and LAN agents.
  2. Add or discover a project. Confirm the project root, execution host, backup destination, and editor/repository shortcuts.
  3. Create one verified backup. Treat this as the baseline before enabling automation or file-changing tools.
  4. Add optional runtime monitoring. PM2, Docker startup gating, and supporting-service probes are independent and can be enabled per project.
  5. Enable recovery history if useful. The delta journal complements full backups; it does not replace them.
Dashboard Map: Projects is the operational workspace, Overview is host/project health, Storage is backup capacity/mirror status, Activity is the audit trail, and Help is this guide.
Projects & Project SettingsLocal vs LAN projects, paths, schedules, editor links, and project actions.
  • Execution Host: Local projects use paths and tools on the UPM host. LAN projects use the selected Remote Agent for supported remote operations.
  • Project Root: Point to the actual source root, normally the folder containing package.json.
  • Editor & Repository: These are convenience links only; they do not affect backup or PM2 matching.
  • Discovery: Scan parent folders for Node projects when registering many local projects.
Tip: If PM2 matching is unreliable because the process runs from another working directory, add explicit PM2 process names in Runtime settings.
Backups, Mirrors, Verification & RestoreRetention, include/exclude rules, secondary destinations, encryption, and safe restore behavior.
  • Change-aware backups: A normal backup can be skipped when source content has not changed. That is expected.
  • Secondary mirror: Primary commit happens first. An unavailable USB/NAS mirror can be caught up later instead of blocking the primary backup.
  • Verification: Verification checks archive integrity/content metadata; use it after storage or transport problems.
  • Excludes: Additional excludes use Git-style patterns. Include overrides can intentionally re-include selected ignored files.
  • Encryption: Encrypted archives require the same AES-256-GCM key for recovery. Keep an offline copy of every key needed for retained archives.
  • Restore: UPM verifies the archive before extraction and blocks restoring directly over the registered project root.
Caution: Force-including secrets such as .env is supported, but encrypted backups are strongly recommended when those files contain credentials.
PM2 Monitoring, Controls & Docker Startup GateMatching processes, safe auto-start, logs/history, and Docker readiness.
  • Monitoring vs controls: Monitoring is read-oriented. PM2 controls and auto-start are separate opt-in settings.
  • Matching: UPM first uses PM2 cwd/script paths, then optional explicit process names.
  • Auto-start: Stopped/offline/missing processes can be started automatically. Errored processes are intentionally not placed in an automatic restart loop.
  • Docker gate: When enabled, UPM waits for docker info to succeed. Docker Desktop merely being open does not mean the daemon is ready.
  • History and logs: Use Process Control, Log, and Health History on project cards to separate a current problem from a recurring one.
Tip: If a project uses containers but PM2 itself does not depend on Docker, leave the Docker gate disabled for that project.
Supporting Service HealthRedis, MariaDB/MySQL, PostgreSQL, Docker, and custom HTTP/TCP probes.

Service Health answers a different question from PM2: "Are the dependencies this project needs reachable?"

  • Use the shortest practical probe interval without creating needless network noise.
  • A Redis authentication-required response can still confirm that the Redis server is reachable.
  • Database probes are protocol-level reachability checks; UPM does not store database passwords for these checks.
  • Custom checks accept Name | http | URL or Name | tcp | host:port.
File Tools & Text SanitizerCopy-oriented utilities, duplicate inventory, and reviewable Unicode cleanup output.
  • Latest File Parser: Selects newest timestamped versions and writes clean names to an output tree.
  • Comment Remover: Uses parser-aware cleanup for supported source formats while preserving the source tree.
  • Inventory + Duplicates: Uses SHA-256 to inventory files and identify exact duplicates.
  • Text Sanitizer: Uses the same copy-oriented output model as the other File Tools workflows; selected sanitized files are written to a separate output tree and source files stay untouched.
  • Sanitizer presets: Standard is conservative; Expanded adds compatibility/fullwidth mappings; Extended/Ambiguous substitutions are higher risk and remain opt-in.
Text Sanitizer: Scan and review highlighted changes, choose a separate output folder, and optionally create a verified UPM project backup before writing sanitized copies.
Recovery, Delta Journal & Change ExportReversible patches, project diffs, feature packs, and last-resort reconstruction.
  • Delta journal: Stores compressed reversible history between successful backup snapshots, with independent retention limits.
  • Project Diff: Compares current project content with the selected/best available backup baseline.
  • Feature Pack: Exports a shareable set of changed files and readable diffs, with an option to omit likely sensitive files.
  • Recovery workspace: Combines available backup, journal, and source-history evidence. Treat suggestions as candidates to review, not guaranteed truth.
Best Practice: Keep both full backups and the delta journal. They protect against different failure modes.
Dependency Health & UpdatesReview installed/requested/latest versions before changing package metadata.
  • Review the requested range and available versions before updating.
  • Pre-release versions are excluded unless explicitly enabled.
  • Lifecycle scripts can execute package-provided code; leave them enabled only when the project expects them.
  • Create a project backup before broad dependency changes so package and lock-file changes are easy to compare or recover.
LAN Remote Agents, Remote Access & SecurityPermission gates, authentication, reverse proxies, agent connectivity, and common 401/403 causes.
  • Remote dashboard: Controls whether non-loopback clients may reach the dashboard.
  • Remote admin/filesystem: These are separate permissions and remain gated behind authentication.
  • Trust Proxy: Enable only when the trusted reverse proxy itself runs on the UPM host and supplies the forwarded client information UPM expects.
  • Secure cookie: Enable only when the browser actually reaches UPM through HTTPS; otherwise the browser will not return the session cookie.
  • LAN Agents: A remote project must reference a configured/reachable agent before remote PM2, service, or backup operations can work.
401 After Login: Check whether Secure Cookie is enabled on an HTTP URL, whether the hostname/origin changed behind a proxy, and whether the session cookie is being returned by the browser.
Runtime Settings & Setup TransferWhat the dashboard can change, what remains secret, and how to move a setup.
  • The Settings dialog edits supported .env runtime options but does not expose stored password hashes, session secrets, encryption keys, or LAN-agent tokens.
  • Setup export/import is intended for moving UPM configuration and project registrations; review warnings before applying an import.
  • Some runtime changes require restarting UPM before the new listener/security behavior is active.
  • Keep backup-encryption keys separately from setup exports.
Desktop, Browser & Build ModesUnderstand runtime differences, then choose Standard, Slim, or Web Installer packaging.
  • Browser Mode: Uses the normal dashboard HTTP session and authentication rules. Native-only controls such as the tray, application menu, and desktop folder picker are not exposed.
  • Desktop App: Hosts the same dashboard locally inside Electron, adds the native menu/tray and directory chooser, and authenticates the embedded renderer with a per-run desktop token that is accepted only from the local machine.
  • Open In Browser: Opens a normal browser session. It intentionally returns to Browser Mode and follows the configured browser authentication and remote-access rules rather than inheriting Electron trust.
  • Standard: Keeps the bundled PM2 CLI fallback and is the most self-contained Windows build.
  • Slim: Keeps only the English Electron locale, omits dependency source maps, uses smart ASAR unpacking, x64-only packaging, and maximum installer compression. System/global PM2 is the fallback when the bundled CLI is unavailable.
  • Web Installer: Produces the smallest setup executable because the application payload is downloaded during install. It does not make the installed Electron runtime itself tiny.
  • Measure it: Run npm run desktop:size after building to list total output size and the largest files in each release folder.
Electron Size Floor: Chromium and Node.js are part of Electron, so large reductions beyond these packaging trims would require moving to a system-WebView desktop shell rather than simply changing compression.
Diagnostics & Troubleshooting WorkflowA repeatable order for investigating failed backups, PM2, services, or configuration.
  1. Open Diagnostics and note the exact error/code.
  2. Check Activity for what immediately preceded the failure.
  3. For PM2 problems, compare current status with Health History and logs.
  4. For backups, confirm the source and destination exist, have free space, and are writable; then run verification.
  5. For LAN projects, verify the Remote Agent first so a host-connectivity problem is not mistaken for a project failure.
  6. After changing settings, retry the smallest affected operation before running Backup All or other broad actions.
Windows EPERM Tip: Rename/replace errors can be caused by antivirus/indexers, another process holding the file, permissions, or a temporarily unavailable destination. UPM uses hardened atomic writes where supported, but the underlying filesystem still has final authority.

Backup destinations & schedule

Control retention, mirroring, change watching, scheduling, encryption, and excludes.

The secondary destination is best-effort. The primary backup is committed first; disconnected USB/NAS mirrors are backfilled when they return.

Scheduled backups
Weekdays

Scheduled checks retain the change-detection rule; unchanged projects are skipped.

Backup encryption ?

Uses AES-256-GCM with the secret from UPM_BACKUP_ENCRYPTION_KEY. Existing backups keep their original encryption state.

The encryption key is never stored in the project configuration. Keep a secure offline copy of the key: encrypted backups cannot be restored if it is lost or changed.

RECOVERY

Persistent delta / change journal

Retain reversible file history independently from full backup rotation.

Delta journal ?

The journal lives under data/delta-journal and is retained independently from full backup archives. When backup encryption is enabled, new journal entries are encrypted with the same AES-256-GCM key. Files above the per-file ceiling are recorded as metadata-only instead of embedding large payloads.

RUNTIME

PM2 monitoring & controls

Match project processes, expose optional controls, and configure safe auto-start behavior.

PM2 monitoring

Automatic matching uses the PM2 working directory and script path first; explicit names are treated as overrides. Auto-start is opt-in, starts stopped/offline matches by PM2 ID, and uses the ecosystem file only when no process is registered. When the Docker wait gate is enabled, UPM holds the project until the Docker daemon answers docker info; Docker Desktop merely opening is not treated as ready. Errored processes are never placed in an automatic restart loop.

SERVICES

Supporting service health

Monitor Redis, databases, Docker, and custom HTTP/TCP dependencies independently from project process state.

Service health monitoring ?

Uses docker info on the project host and reports daemon/container state.

Health checks do not store database passwords. Redis uses PING (an authentication-required response still confirms the server is reachable), MariaDB/MySQL and PostgreSQL use protocol handshakes, and LAN projects run these checks on their selected remote agent.
